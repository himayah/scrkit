# Windows 標準 `.scr` の調査と SCRAPI v2 ドラフト仕様

> 状態: **調査 + ドラフト(未実装)**。[`SCRAPI_SPEC.md`](SCRAPI_SPEC.md)(v1、実装済み・main 統合済み)
> を置き換えるものではなく、その上に積む拡張案をまとめたもの。本書のいかなる項目も、実装され
> `SCRAPI_SPEC.md`側に統合されるまでは仕様として確定しない。
>
> 目的: (A) Windows が `.scr` に対してそもそも何を規定していて何を規定していないかを調査し、
> (B) 現行 SCRAPI v1 / ScrKit.scr が既にカバーしている範囲を整理し、(C) 一般的なスクリーン
> セーバーに求められがちな機能を俯瞰した上で、(A)〜(C) を貫く**特定のセーバー実装に依存しない**
> 一般化されたAPI拡張を設計する。

## 0. 前提: 「Windows 標準の `.scr` にAPIを付与する」の意味

Windows は `.scr` という**ファイル形式**そのものにはプラグイン機構や拡張APIを一切持たない。
`.scr` は単に `.exe` を改名しただけの通常の Win32 GUI 実行ファイルで、Windows 側が規定するのは
起動時のコマンドライン引数の意味づけ(§A.1)と、それをいつ起動するかを決める Explorer/Winlogon
側の設定(§A.2)だけである。つまり「Windows 標準の `.scr` に API を付与する」とは、Windows 自体
を変更することではなく、**その最小限の契約を壊さずに、既存の `/p` 実行時だけ帯域外(out-of-band)
の追加チャンネルを開く**という、まさに SCRAPI v1 が採った設計そのものである。本書の§Aはこの
前提を実機調査ではなく公開情報の調査で裏付け、§B〜Dでその上に何を足せるかを検討する。

## A. Windows 標準 `.scr` の実態調査

### A.1 プロセス契約(コマンドライン)

Windows が実際に規定しているのはこれだけである(本プロジェクトの `WinMain.cpp` の実装もこれに
準拠している):

| スイッチ | 意味 | 備考 |
|---|---|---|
| `/s` | フルスクリーンでスクリーンセーバーを実行 | 引数なし |
| `/c` または `/c:<hwnd>` | 設定ダイアログを表示 | `:hwnd` は呼び出し元ウィンドウ(任意、モーダル化用) |
| `/p <hwnd>` または `/p:<hwnd>` | 指定ウィンドウの子として埋め込みプレビュー描画 | 数値 `hwnd` の渡し方は呼び出し元(コントロールパネル/設定アプリ)によって別引数/コロン付きの2通りがあり、両対応が必要 |
| (引数なし・不明な引数) | 設定ダイアログにフォールバック | Windows 自身の慣習に合わせる |

歴史的に語られる `/a:<hwnd>`(パスワード変更)は Windows 9x 時代の名残で、ログオン方式が統合
された Vista 以降は実質的に使われていない。**Windows は上記4通り以外の呼び出し規約を持たない**
——つまり「規定の拡張ポイント」はこの4つの意味づけそのものであり、SCRAPI v1 が `/p` に
`/scrapi:<pipeName>` という**追加の引数**を足すだけで済ませているのは、この契約を壊さない唯一
現実的な方法である。

### A.2 OS側の設定サーフェス(レジストリ)と `.scr` プロセスとの関係

`.scr` が「いつ・どのモードで」起動されるかは `.scr` 自身ではなく、Explorer/設定アプリと
Winlogon が `HKEY_CURRENT_USER\Control Panel\Desktop` を介して制御する:

| 値 | 意味 |
|---|---|
| `SCRNSAVE.EXE` | 現在選択されている `.scr` の絶対パス |
| `ScreenSaveActive` | スクリーンセーバー機構自体の有効/無効 |
| `ScreenSaveTimeOut` | アイドル秒数(この秒数操作がないと `/s` が起動される) |
| `ScreenSaverIsSecure` | 「再開時にログオン画面を表示」——**実体は Winlogon によるワークステーションロック**であり、`.scr` プロセス自身はパスワード処理に一切関与しない |

重要な点: これらは**`.scr` の実行が終わった後・始まる前**の話であり、実行中の `.scr` プロセスが
自分でこれらの値を読み書きする標準の仕組みはない(読むこと自体は任意の一般アプリと同じレジストリ
APIで可能だが、Windows がそれを「.scr向けAPI」として用意しているわけではない)。SCRAPIのような
プロトコルが対象とするのは**あくまで実行中の1プロセスとビュワーの対話**であり、この節の値は
本書§D.6で「SCRAPIとは別のビュワー側コンビニエンス機能」として扱う。

### A.3 セキュア再開(ロック)の責任分界点 -- 明示的な非対象

`ScreenSaverIsSecure=1` の場合、`.scr` のウィンドウが閉じた後にユーザーの認証を要求するのは
Winlogon(ロック画面)であり、**`.scr` 自身が「パスワードを検証する」機能を持つことは Windows
の設計上あり得ないし、あってはならない**。将来 SCRAPI にどんな機能を足すとしても、認証・
ロック解除に類する機能をセーバー側のAPIとして持たせることは明確な非対象とする(§Fで再掲)。

### A.4 マルチモニタの扱いとギャップ

Windows は複数モニタを「拡張」設定にしている場合、すべてのモニタを結合した**単一の仮想画面**
として `.scr` を1プロセスだけ起動する(モニタごとに別プロセスを立てるような調整機構は存在
しない)。標準の一部セーバー(3D テキスト等)は意図的にプライマリモニタにしか描画せず、
モニタごとに異なる内容を出したい場合は `.scr` 自身が `EnumDisplayMonitors` で座標を取得して
自前で描き分けるしかない。**ScrKit.scr 自身は現状これを対象外としており**(`docs/DESIGN.md`
「マルチモニタは対象外とし、プライマリディスプレイの解像度のみを使用する」)、プライマリの
解像度(`SM_CXSCREEN`)のみを使っている。これはWindows側の欠落であり、SCRAPIのような
セーバー非依存の仕様がモニタトポロジをビュワーに申告する語彙を持てば、対応したいセーバー
だけがそれを使える(§D.3)。

### A.5 その他のOSフックの現状(調査結果、いずれも本書の対象外/参考情報)

- `SystemParametersInfo(SPI_GETSCREENSAVERRUNNING / SPI_SETSCREENSAVERRUNNING)`: Windows 9x/NT5
  世代の名残で、現行の NT カーネル(Vista 以降)では実質的に無効化されており使う意味がない。
- `GetLastInputInfo`(アイドル検出): 任意の一般プロセスが使える汎用APIであり、`.scr` 固有の
  ものではない(そもそも `/s` が起動する時点でOSは既にアイドルと判断済み)。
- 結論: **Windows は `.scr` に対して拡張APIを持たない**。よって「Windows標準の.scrにAPIを
  付与する」の実質的な答えは、A.1の契約を壊さない帯域外チャンネル(=SCRAPI)を、A.2〜A.4で
  洗い出したOS側の欠落・境界を意識しながら育てること、という結論になる。

## B. 現行 SCRAPI v1 / ScrKit.scr の到達点(要約)

詳細は [`SCRAPI_SPEC.md`](SCRAPI_SPEC.md) 参照。既に実装済みの範囲を要約する:

| 領域 | 内容 |
|---|---|
| 起動・接続 | `/p <hwnd> /scrapi:<pipeName>`、名前付きパイプ、JSON Lines |
| 操作 | `hello`/`manifest`/`get`/`set`/`invoke`/`subscribe`/`bye` |
| コントロール型 | `group`/`enum`/`flags`/`bool`/`int`/`float`/`string`/`color`/`path`/`button`/`readout` |
| 条件式 | `visibleWhen`/`enabledWhen`(`eq`/`in`/`all`/`any`/`not`) |
| 標準コントロール | `scrapi.paused`/`timeScale`/`step`/`seed`/`restart`/`fps`/`saveToConfig` |
| 伝送の抽象化 | 「順序保証のあるバイトストリーム」であればよく、名前付きパイプは v1 の標準バインディングに過ぎない |

v1 の§9(将来拡張の余地)が既に自己申告している未定義項目: `vec2`/`rect` 型、`image` 型、
プリセット保存の標準化、セーバー→ビュワー方向の要求、埋め込み以外の表示方式。本書はこれらに
具体案を与え(§D)、さらにその外側(マルチモニタ・アクセシビリティ・省電力・OS連携)まで
範囲を広げる。

## C. 需要調査: 一般的なスクリーンセーバーに求められがちな機能とAPIとしての要否

| 機能領域 | 具体例 | 現行v1でカバー可能か | 必要な対応 |
|---|---|---|---|
| エフェクト/表示切替 | 効果選択・強度・配色 | **可能**(`enum`/`float`/`color`) | なし |
| 音声反応(オーディオビジュアライザ) | 音量・周波数バンドをビジュアルに反映 | **可能**(ビュワーが高頻度に`set`で`float`系コントロールへ書き込むだけ。専用の型もオペも不要) | 慣習として`input.*`名前空間を推奨(§D.5) |
| ライブ/外部コンテンツ | フォルダの写真・時計・簡易システム情報 | 一部可能(`path`でフォルダ指定は可) | 大きな2値データ(写真そのもの)の転送は不可 → `image`型(§D.1) |
| プリセット/プロファイル | 設定一式の保存・読込・共有 | 不可(v1 §9 記載の既知ギャップ) | `scrapi.presets.*`(§D.2) |
| マルチモニタ | モニタごとに異なる内容/配置 | 不可 | `scrapi.displays`(§D.3)。ScrKit.scr自体の実装は別途(現状スコープ外) |
| アクセシビリティ | モーション低減・配色配慮 | 慣習で可能だが未定義 | `scrapi.reducedMotion`等(§D.5) |
| 省電力/性能適応 | バッテリー時にFPSを落とす | 慣習で可能だが未定義 | `scrapi.powerSaver`/`targetFps`(§D.5) |
| リモート/ネットワーク越し制御 | 別PC・スマホアプリからの操作 | **伝送層は既に抽象化済み**(§3「将来の別バインディング」) | 認証・暗号化の設計が別途必要(§Fで非対象と明記) |
| 複数`.scr`のプレイリスト化 | 時間帯で切り替え | ビュワー側の仕事(単に別の`.scr`を起動するだけ) | SCRAPI変更不要 |
| セーバーからビュワーへの問い合わせ | 「ファイルを選んで」等 | 不可(v1は要求がビュワー→セーバーのみ) | `viewerInvoke`(§D.4) |
| デバッグ/診断表示 | 現在の内部状態のスナップショット | `readout`で数値・短文は可能。画像は不可 | `image`型(§D.1) |
| テレメトリ/使用状況収集 | (一般的な商用セーバーにはあるが) | -- | **意図的に非対象**(§F、本プロジェクトの禁止事項方針に合わせる) |

## D. SCRAPI v2 提案仕様(具体案)

すべて**加算のみ**(v1のクライアント/セーバーは無視して動作を継続できる)で、`scrapi` バージョン
は `1.1` への更新を想定する(§Eのルール上、マイナー更新は後方互換な追加のみに限られるため)。

### D.1 新コントロール型: `vec2` / `rect` / `image`

| type | 値の型 | 固有プロパティ | 用途 |
|---|---|---|---|
| `vec2` | `{"x":number,"y":number}` | `min`/`max`(各軸)、`space`: `normalized`(既定、0..1)/`pixels` | プレビュー上のクリックで位置指定(吸い込み中心など) |
| `rect` | `{"x","y","w","h"}` | `space`(同上) | 領域選択(クロップ範囲・注目領域) |
| `image` | Base64(`data`)または一時ファイルパス(`path`) | `mimeType`(`image/png`推奨)、`maxBytes`(既定256KiB。超える場合は`path`方式を使うこと) | セーバー→ビュワーのサムネイル/デバッグ画像。ScrKit.scr の `debug.dump`(ファイル書き出し)は、この型が実装されればプロトコル内蔵の`readout`相当に置き換えられる |

`vec2`/`rect` はビュワー側で埋め込みプレビュー上のドラッグ操作からピクセル座標を`space:"pixels"`
で送るのが典型利用。`image`はまず小さな`readout`用途(状態プレビュー)に限定し、動画的な連続
転送(=事実上の別レンダリングパス)は明確に対象外とする(v1設計原則2「段階的に劣化する」を
壊すほど重い機能はSCRAPIの範囲を超える)。

### D.2 プリセット標準化: `scrapi.presets.*`

| id | 型 | 意味 |
|---|---|---|
| `scrapi.presets.list` | `readout`(文字列配列) | 保存済みプリセット名の一覧 |
| `scrapi.presets.save` | `button`(`args:{"name":string}`) | 現在の値一式を名前付きで保存(セーバー側の設定ファイルへ。§7の永続化ルールに従い`confirm`推奨) |
| `scrapi.presets.load` | `button`(`args:{"name":string}`) | 指定プリセットを適用し`manifestChanged`/`changed`を発火 |
| `scrapi.presets.delete` | `button`(`args:{"name":string}`) | 削除 |

既存の`scrapi.saveToConfig`(現在の値をセッション超えて保存)とは独立: `saveToConfig`は
「今の状態を既定にする」、`presets.*`は「名前付きで複数保持する」。

### D.3 マルチモニタ対応: `scrapi.displays` とターゲット指定

```jsonc
// readout の値の例
{"scrapi.displays": [
  {"index": 0, "primary": true,  "x": 0,    "y": 0, "w": 2560, "h": 1440},
  {"index": 1, "primary": false, "x": 2560, "y": 0, "w": 1920, "h": 1080}
]}
```

- `scrapi.displays`(`readout`、配列): 対応セーバーはOSのモニタ構成が変わるたびに`changed`で
  更新する。未対応セーバーは単に持たない(ビュワーは`capabilities`に`scrapi.displays`が
  無ければ単一画面前提のUIのまま)。
- コントロールノードに任意の`targetDisplay`(int、`scrapi.displays`の`index`を参照)プロパティを
  追加可能とし、「このコントロールはこのモニタの層にだけ影響する」ことを宣言できるようにする
  (例: モニタごとに別の壁紙ソースを選ばせたい場合の`enum`ノードを、モニタの数だけ`group`化)。
- **ScrKit.scr自身がマルチモニタに対応するかは別課題**(`docs/DESIGN.md`記載のとおり現状は
  プライマリのみ)。本項はSCRAPIというプロトコル側の語彙を用意するだけで、実装は各セーバーに
  委ねる(v1の「セーバー実装に依存しない」設計原則どおり)。

### D.4 ビュワー機能をセーバーから呼ぶ: `viewerInvoke`

v1は要求がビュワー→セーバーの一方向のみ。`path`型の「参照」ボタンのように、セーバー側の
都合でビュワーに何かを頼みたい場面(ファイル選択ダイアログの表示、通知の表示、確認ダイアログ)
に対応するため、**ビュワーが対応する機能を`hello`要求自体に申告**し、対応する場合だけセーバーが
逆方向の要求を送れるようにする:

```jsonc
// ビュワー → セーバー (hello 要求。viewerCapabilities を追加)
{"op":"hello","apiVersion":"1.1","client":"ScrViewer/1.0","viewerCapabilities":["viewer.pickFile","viewer.notify"]}
// セーバー → ビュワー (新オペ。ビュワーがhelloで申告した機能のみ送ってよい)
{"id": 1, "op": "viewerInvoke", "action": "viewer.pickFile", "args": {"filters":[{"label":"Images","pattern":"*.png;*.jpg"}]}}
// ビュワー → セーバー (応答。id はセーバーの採番)
{"id": 1, "ok": true, "results": {"path": "C:\\...\\photo.jpg"}}
```

`viewerInvoke`はセーバー側が採番する独立した`id`空間を持つ(v1の`id`はビュワー採番のリクエスト
用と衝突しないよう、実装上は同じフィールド名でも起点で区別できるため問題ない)。ビュワーが
`viewerCapabilities`を送らない(=v1のまま)場合、セーバーは`viewerInvoke`を一切送ってはならない
——これによりv1のビュワー実装は変更なしに動き続ける(後方互換)。

### D.5 アクセシビリティ・省電力の慣習コントロール

新しい予約`scrapi.*`コントロール(すべて任意実装):

| id | 型 | 意味 |
|---|---|---|
| `scrapi.reducedMotion` | bool | OSの「視覚効果を減らす」設定に相当。trueならセーバーは激しい動き・点滅を控えめにする |
| `scrapi.powerSaver` | bool | バッテリー駆動などでビュワー/OS側が真にする。trueなら描画負荷を下げることが期待される |
| `scrapi.targetFps` | int | ビュワー側が推奨するフレームレート上限(省電力/固定フレームレート要求向け) |

いずれも「ビュワー側が状況を検知し、値をセーバーに`set`する」だけの通常のコントロールであり、
新しい型やオペを必要としない——挙動をどう変えるかはセーバー実装に委ねる、というSCRAPI全体の
設計原則(§1「セーバー実装に依存しない」)にそのまま従う。

### D.6 OS連携コンビニエンス層(SCRAPIプロトコル外、ビュワー側機能)

§A.2で調査したレジストリ値(`SCRNSAVE.EXE`/`ScreenSaveActive`/`ScreenSaveTimeOut`/
`ScreenSaverIsSecure`)は`.scr`プロセスの外側の話であり、SCRAPIセッション(§3〜§8)には
一切含めない。その代わり、ScrViewerのような「セーバーを管理するアプリ」が**通常のWindows
レジストリAPIを使い、ユーザーの同意を得た上で**次のような便宜機能を持つことを提案する
(SCRAPIバージョニングとは無関係、いつでも実装可):

- 「このセーバーをWindowsの既定に設定する」ボタン(`SCRNSAVE.EXE`の書き換え)
- タイムアウト・「再開時にロック」のGUI(レジストリ値の読み書き)

これは`.scr`本体のAPIではなく、ビュワー(または将来の設定アプリ)が持つ機能として明確に
切り分ける——§A.3の責任分界点(認証はWinlogonの仕事)を侵さない範囲に留める。

## E. バージョニングと後方互換性

- 本書の提案はすべて`scrapi: "1.1"`として、v1の後方互換ルール(§8: マイナーは追加のみ)に
  従う設計にした。`viewerInvoke`(§D.4)のみ双方向性を持つが、ビュワーが明示的に
  `viewerCapabilities`を申告しない限りセーバーは送らないため、v1のビュワー実装は無改修で
  動き続ける。
- 実装するセーバー/ビュワーは、本書のどの項目を実装したかを`capabilities`配列(既存の仕組み)
  にそのまま列挙する。新オペ・新型を使う前に相手の`apiVersion`/`capabilities`を確認する
  という既存のv1の作法をそのまま延長する。

## F. 明示的な非対象

- **認証・ロック解除**: `ScreenSaverIsSecure`の実体はWinlogonの責務であり、SCRAPIにパスワード
  検証・認証系の機能を持たせることは今後も行わない(§A.3)。
- **Windows自体の変更**: `.scr`のコマンドライン契約(`/s`/`/c`/`/p`)そのものを変える提案は
  含まない。SCRAPIは常に`/p`実行時の追加チャンネルという立場を維持する(v1設計原則1)。
  複数モニタへ**個別のプロセスとして**セーバーを分散起動するようなOS側の変更も対象外——
  §D.3はあくまで単一プロセス内でのモニタ認識の語彙に留める。
- **テレメトリ・ネットワーク送信**: 使用状況の収集、外部サーバーへの送信、広告等は一切対象外
  (本プロジェクトの既存方針・要件.txtの禁止事項に合わせる)。伝送層の抽象化(§3)は将来の
  ローカル/リモートバインディングの**可能性**を閉じないためのものであり、リモートバインディング
  自体の認証・暗号化設計は本書のスコープ外(実際に着手する段になって初めて設計する)。
- **動画的な連続画像転送**: `image`型(§D.1)はスナップショット用途に限定し、フレームバッファの
  ストリーミングのような重い用途はSCRAPIの範囲外(そこまで必要なら共有テクスチャ等、埋め込み
  方式自体の再設計が要る──v1 §9が既に「埋め込み以外の表示方式」として保留している領域)。

## G. 実装優先度の提案(参考、確定ではない)

1. `scrapi.presets.*`(§D.2) -- 既存の`get`/`set`/`invoke`だけで実現でき、追加の型もオペも
   不要。実装コストが最も低い。
2. `scrapi.reducedMotion`/`powerSaver`/`targetFps`(§D.5) -- 同様に既存の`bool`/`int`型で
   即実装可能。
3. `vec2`/`rect`型(§D.1) -- ビュワー側にクリック/ドラッグ座標をプレビュー座標系へ変換する
   処理が要るが、プロトコル自体は単純。
4. `scrapi.displays`(§D.3) -- ScrKit.scr自身のマルチモニタ対応(現状スコープ外)とセットで
   検討するのが自然。プロトコル語彙だけ先に決めても、使うセーバーが無ければ検証できない。
5. `image`型・`viewerInvoke`(§D.1後半・§D.4) -- 実装・セキュリティ考慮(任意ファイルパスを
   ビュワーに渡す`viewer.pickFile`等)の両面で最も慎重な設計が要る。優先度は最後。
